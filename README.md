## What This Package Does

`fca-azadx69x` logs in with a Facebook session, builds an API object, loads the
modules in `src/`, and connects to Facebook web messaging endpoints and MQTT.
It is intended for personal automation, bot development, moderation tools, and
Messenger utilities.

The package uses Facebook web behavior that is not a stable public API. Facebook
can change request formats, GraphQL operation IDs, cookies, checkpoints, or MQTT
behavior without notice.

## Requirements

- Node.js 14 or newer for this FCA package.
- A valid Facebook `appState` is the recommended login method.
- Network access to Facebook web and MQTT endpoints.
- A writable working directory for runtime state files.
- Node.js 22 or newer when running the complete parent X69X BOT project.
- **A stable egress IP and one account per fingerprint.** Running many accounts
  from one IP, or one account from changing IPs, is the fastest route to a
  checkpoint. See [Checkpoints and Account Safety](#checkpoints-and-account-safety).

## Installation

From the parent project:

```bash
npm install
```

Use this local package from a bot:

```js
const { login } = require("./fca-azadx69x");
```

The FCA package declares its own dependencies in `fca-azadx69x/package.json`.
The parent bot currently also provides shared dependencies used by some FCA
modules, including `request` and `npmlog`. Verify those dependencies when using
the FCA directory outside the parent project.

## Quick Start

```js
"use strict";

const { login } = require("./fca-azadx69x");
const appState = require("./appstate.json");

login(
  { appState },
  {
    listenEvents: true,
    autoMarkRead: true,
    autoReconnect: true,
    online: true
  },
  (error, api) => {
    if (error) {
      console.error("Facebook login failed:", error);
      return;
    }

    console.log("Logged in as:", api.getCurrentUserID());

    api.listenMqtt((listenError, event) => {
      if (listenError) {
        console.error("Listener error:", listenError);
        return;
      }

      if (event.type !== "message" || !event.body) return;

      api.sendMessage(
        `You said: ${event.body}`,
        event.threadID,
        event.messageID
      );
    });
  }
);
```

## Login Input

The recommended login input is a Facebook `appState` array:

```js
{
  appState: [
    { key: "c_user", value: "..." },
    { key: "xs", value: "..." },
    { key: "fr", value: "..." }
  ]
}
```

Legacy entries using `name` instead of `key` are normalized. A semicolon-delimited
appState string is also accepted by the login helper. The internal login flow
also has email/password parameters, but Facebook may require checkpoint,
device approval, or two-factor verification. Use a fresh appState when possible.

> Treat appState as a password. Never commit it, paste it into a README, or
> send it in an issue, screenshot, or chat.

## Login Options

Options are passed as the second argument to `login`:

| Option | Default | Purpose |
| --- | --- | --- |
| `selfListen` | `false` | Receive events generated by the logged-in account |
| `selfListenEvent` | `false` | Receive self-generated non-message events |
| `listenEvents` | `true` | Enable event delivery |
| `listenTyping` | `false` | Listen for typing events |
| `updatePresence` | `false` | Publish presence updates |
| `online` | `true` | Keep the session online |
| `autoMarkDelivery` | `false` | Mark received messages as delivered |
| `autoMarkRead` | `true` | Mark received messages as read |
| `autoReconnect` | `true` | Reconnect MQTT after recoverable failures |
| `forceLogin` | `false` | Refresh an existing session during login |
| `userAgent` | Built-in | Set a custom browser user-agent |
| `randomUserAgent` | `false` | Select a supported random user-agent |
| `pageID` | None | Use a Facebook Page messaging context |
| `proxy` | None | Use a supported HTTP or SOCKS proxy |
| `bypassRegion` | Automatic | Force an MQTT region such as `ash` or `ftw` |
| `emitReady` | `false` | Emit the ready event when supported |

> **Do not set `userAgent` or `randomUserAgent` in normal use.** The
> anti-suspension layer assigns one stable fingerprint per account and reuses it
> for the whole session. Overriding it manually, or setting `randomUserAgent:
> true`, reintroduces the exact per-session drift that triggers account locks.
> Use these options only when you know the fingerprint you need.

## How It Works

1. `login()` normalizes the supplied session and creates the Facebook request
   context.
2. The account's browser fingerprint is loaded (or assigned once) and persisted
   to `session_fingerprint.json`.
3. The login flow checks the Facebook response for known checkpoints.
4. The API factory loads every `.js` file from `src/`.
5. MQTT listeners deliver incoming events through `(error, event)` callbacks.
6. A quiet keep-warm loop starts, pinging roughly every 25-55 minutes.
7. API methods use the logged-in cookie jar for Facebook requests.
8. Runtime and checkpoint information can be persisted as local JSON files.

The loader exposes each source filename as `api.<moduleName>`. If a module
returns an object, its object methods are also copied onto `api`.

## Runtime Helpers

The following modules return grouped helpers rather than one single function:

```js
const health = api.runtimeHealth.getRuntimeHealth();
const info = api.runtimeInfo.getRuntimeInfo();

console.log(health.status, health.consecutiveErrors);
console.log(info.userID, info.mqttConnected, info.messagesSent);
```

`api.conversationState` provides local per-thread state and locks:

```js
api.conversationState.updateConversationState(threadID, {
  data: { lastCommand: "help" }
});

const state = api.conversationState.getConversationState(threadID);
```

`api.threadCache` provides thread metadata helpers, and `api.threadColors`
contains the supported color constants for `changeThreadColor`.

### Session status

`session.getStatus(ctx, jar)` reports the live state of a session, including the
fingerprint that is currently locked in and whether a checkpoint is cooling down:

```js
const { login, session } = require("./fca-azadx69x");

const status = session.getStatus(ctx, jar);
console.log(status.loggedIn, status.userID, status.cookieCount);
console.log(status.mqttConnected, status.typingThreads);
console.log(status.checkpoint.bypassAttempts, status.checkpoint.coolingDown);
```

`utils.getRuntimeSnapshot(ctx)` returns the same runtime counters on their own.

### Anti-suspension helpers

```js
const { antiSuspension } = require("./fca-azadx69x/utils");

// Which browser fingerprint this account is pinned to
console.log(antiSuspension.fingerprintFor(ctx));

// Current limiter usage (requests in the last 60s, configured ceiling)
console.log(antiSuspension.getRateSnapshot(ctx));

// Manually send one quiet warm-up request
await antiSuspension.warmSession(ctx, jar, utils, globalOptions);

// Start/stop a custom keep-warm loop (normally started automatically on login)
const loop = antiSuspension.startWarmLoop(ctx, jar, utils, globalOptions, {
  minMinutes: 25,
  maxMinutes: 55
});
loop.stop();

// Classify an error before deciding whether it is safe to retry
const signal = antiSuspension.classifySessionSignal(error);
// signal.kind   -> "expired" | "checkpoint" | "blocked" | "unknown"
// signal.action -> "refresh" | "pause"    | "stop"    | "ignore"
```

## Fixes and Behaviour Changes

This section records what changed, so behaviour is not a surprise when
upgrading. Each entry states what the old behaviour was and why it mattered.

### Attachment upload crash

**Old:** `uploadAttachment` read `resData.payload.metadata[0]` and handed it
straight to `Object.keys(file)`. When Facebook returned an empty metadata array
or an error body, `file` was `undefined` and the whole send threw:

```text
ERR! uploadAttachment TypeError: Cannot convert undefined or null to object
    at Object.keys (<anonymous>)
```

**Now:** `utils.extractUploadMetadata()` unwraps the reply safely and returns
`null` for empty/error shapes. Upload failures surface as a clean callback error
and the bot keeps running. Fixed in `sendMessage.js`, `sendMessageMqtt.js`, and
`uploadAttachment.js`.

### Typing indicator accuracy

**Old:** group vs. user was decided by `threadID.length >= 16`. Short group IDs
were sent as user threads, so typing never appeared in those groups.

**Now:** `src/sendTypingIndicator.js` resolves the real thread type with
`api.getThreadInfo()`, caches it per thread, and only falls back to the length
heuristic for deleted or inaccessible threads. It also adds a 5s lookup timeout,
an HTTP GraphQL fallback, a legacy MQTT fallback, and per-thread auto-stop
timers. The public callback/Promise contract is unchanged
(`callback(null, true)` / resolves `true`).

### Checkpoint detection

**Old:** detection relied on exact substring matches such as `/checkpoint/` and
`/checkpoint/block/?next`, so slightly different pages were missed.

**Now:** detection matches checkpoint URLs, block pages, and known checkbox text
(`automated behavior`, `unusual activity`, `suspended`, `locked`, ...). Token
extraction gained multiple fallbacks for `fb_dtsg`, `jazoest`, and `lsd`,
including hidden form inputs, and responses expose `statusCode`. New
`checkpoint.getStatus()` and `checkpoint.resetBypass()` helpers were added.

### Session cleanup and logout

**Old:** `logout()` re-threw inside its callback, so a throwing callback left a
half-open session. Typing timers and caches survived logout.

**Now:** logout callback errors are caught and logged; `clearSession()` also
clears typing timers, pending thread lookups, the thread-type cache, and thread
metadata. Cookie parsing reads `jar.getCookies(...).find(c => c.key === name)`
as well as the raw cookie string.

### Session recovery

**Old:** `withSessionRecovery` re-logged in on 401/403 with no limit, and also
on errors that were not expiry at all.

**Now:** expiry (401/403 / `Not logged in.`) triggers **at most one** re-login
per 5 minutes. Checkpoints and fatal blocks are never retried.

### Runtime state files

A new file was added:

- `session_fingerprint.json` — the browser fingerprint pinned to each account
- `request_rate.json` — reserved for the rate limiter state

## Events

The MQTT listener calls `(error, event)`. Common event types include:

- `message`
- `message_reply`
- `message_reaction`
- `message_unsend`
- `event`
- `read_receipt`
- `typ`
- `presence`

A message event commonly contains:

```js
{
  type: "message",
  threadID: "123456789",
  senderID: "987654321",
  messageID: "mid....",
  body: "Hello",
  attachments: [],
  mentions: {}
}
```

Always check `event.type` before reading type-specific fields. Facebook can send
system events without a `body`.

## Checkpoints and Account Safety

The checkpoint module detects and classifies known flows, including:

- Automated behavior warnings
- Account locks
- Account suspensions
- Device approval
- Two-factor authentication
- Unknown checkpoint pages

Warnings that can safely be dismissed may be handled by the library. Locked,
suspended, 2FA, device approval, and unknown flows require normal browser
verification. No automation library can guarantee that an account will never be
restricted. Use a real account responsibly, avoid spam, and follow Facebook's
terms and policies.

### Why accounts were getting logged out so fast

Earlier builds had a bug that caused exactly this: `getHeaders()` in `utils.js`
generated a **new random `User-Agent` on every single HTTP request**, and also
randomly added or removed `Sec-Fetch-*`, `DNT`, and `Referer` headers per
request.

To Facebook, one cookie set arriving as Chrome 120, then Firefox 122, then Mac
Safari inside a few seconds is the strongest possible "automation / account
takeover" signal. It produced, reliably:

- checkpoint `601051028565049` — automated behavior / scraping warning
- checkpoint `828281030927956` — **account locked, identity/unvetted flow**

That per-request randomization has been removed. A fingerprint is now chosen
once per account and reused for the whole session.

### Anti-suspension layer (`antiSuspension.js`)

| Layer | What it does | Why it helps |
| --- | --- | --- |
| Fingerprint lock | One `User-Agent` + `sec-ch-ua` + platform + locale per account, persisted to `session_fingerprint.json` | Facebook never sees the same cookie set pretend to be several different browsers |
| Account isolation | Two accounts never receive the same fingerprint | Prevents duplicate-device-fingerprint checkpoints |
| Human-like rate limiter | Minimum gap between requests + rolling ceiling of 40 requests/minute + jittered burst cooldown | Stops the burst pattern that reads as a bot |
| Quiet keep-warm loop | One silent `GET /` every ~25-55 minutes (randomised, self-rescheduling) | Keeps the cookie jar warm so the session is not expired for inactivity |
| Signal classification | Separates `expired` (retry), `checkpoint` (stop), and `blocked` (fatal) | Retrying a hard block is what turns a warning into a permanent lock |

### What NOT to do

These escalate a warning into a real lock. The library deliberately refuses to
do them:

- Retrying after `Facebook blocked the login` (`error: 1357001`)
- Re-logging in repeatedly after a checkpoint, lock, suspension, or 2FA prompt
- Changing the `User-Agent` or device fingerprint mid-session
- Logging the same account in from many IPs, or many accounts from one IP
- Bursting requests (mass friend requests, mass sends, rapid loops)

If an account is already locked, **stop the bot for that account**. Open
`facebook.com` in a normal browser on a trusted device, complete the identity
verification, wait 24-48 hours, then export a fresh `appState` and start again.
Repeated automated login attempts extend the lock timer.

## Known Limitations

- Facebook private web endpoints and GraphQL operation IDs can expire or change.
- A valid session can still be rejected by Facebook or require a checkpoint.
- Profile photos may be unavailable even when profile data is returned.
- `searchGif` is not implemented in this FCA build; `searchStickers` is the
  available built-in search module.
- `npm test` currently exits with `Error: no test specified`; use syntax checks
  and focused integration tests until a package test suite is added.
- The package metadata does not currently list every dependency imported by all
  source files. Standalone users should verify `request` and `npmlog` in
  particular; the parent bot already declares them.
- The anti-suspension layer reduces risk but cannot make a restriction
  impossible. Account safety still depends on behaviour, IP stability, and how
  the account is used outside the bot.
- Only one process per account is safe to run. Two processes sharing an account
  produce competing MQTT sessions and duplicate requests.

Check the main files before opening a pull request:

```bash
node --check index.js

node --check checkpoint.js
```
